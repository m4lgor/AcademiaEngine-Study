Course engine reference

AcademiaEngine

AcademiaEngine runs the game loop, keeps track of your objects and converts positions into pixels for drawing. You write the game inside it.

Run it

Open AcademiaEngine.sln in Visual Studio, pick Debug | x64 and press F5. A 1024 by 1024 window opens with one white circle in the middle. That circle is the example object.

You are free to read and change the engine, including main.cpp and src/Engine. The goal of this course is that you understand how it works and why it is built this way, so read it. Gameplay lives in src/Game and everything physics lives in src/Physics.

GameObjects

Anything that exists in your game (a player, a bullet, a wall) is a class that derives from GameObject. It has a Position in world units and two functions you can override: Update(elapsedTime) for behavior and Draw(engine) for rendering. The engine calls both for you on every object in the Scene.

class Player : public GameObject
{
public:
    void Update(float elapsedTime) override
    {
        // Move right at 3 world units per second
        Position.x += 3.0f * elapsedTime;
    }

    void Draw(AcademiaEngine& engine) override
    {
        Vector2i pixels = engine.ConvertWorldPositionToPixels(Position);
        int radius = (int)engine.ConvertWorldLengthToPixels(0.4f);
        engine.FillCircle(pixels, radius, olc::YELLOW);
    }
};

Always multiply movement by elapsedTime. The game then moves at the same speed on a slow or a fast computer.

Why it works this way

You never write the game loop. The engine owns it and calls your Update and Draw. This is called inversion of control: the engine is a framework that calls you, not a library you call.

The benefit is that the engine can change what happens around your code (pause it, step it, draw tools over it) without you changing a line. Update and Draw are separate functions so that logic can stop while the picture stays on screen.

New file? Add it to the project (right-click src/Game, Add, New Item), or it will not compile.

Scene

The Scene holds every GameObject. Get it with _EngineContext->GetScene() inside GameManager.

// In GameManager::Initialize
_Player = _EngineContext->GetScene().Add<Player>();   // Player* _Player member
_Player->Position = { 0.0f, 0.0f };

// In GameManager::Uninitialize
_EngineContext->GetScene().Remove(_Player);
_Player = nullptr;
CallWhat it does
Add<T>(args...)Creates an object of type T and returns a pointer to it. Constructor arguments are passed through.
Remove(object)The object is deleted at the end of the frame. Do not use the pointer after this call.
Clear()Removes every object, for example to start a new level.
GetObjectCount()How many objects are alive. Shown in the stats panel.

Whoever adds an object removes it

This works like new and delete. The code that calls Add is responsible for calling Remove, usually in Uninitialize. The pointer you get is only a view of the object: set it to nullptr after you remove it.

If you forget, the engine tells you when the game closes, with the name of each object left behind:

Scene: 1 object(s) were added but never removed. Whoever calls Scene::Add must call Scene::Remove.
  - class Player

An object does not remove itself. If a gun adds bullets, the gun keeps track of them and removes them.

Add and Remove wait for the end of the frame

An added object is updated from the next frame, and drawn at the end of this one. A removed object is skipped for the rest of this frame and deleted at the end of it. This makes both safe to call from inside an Update.

Why it works this way

Add and Remove wait because the Scene is looping over its list of objects while your Update runs. Adding or removing an item from a list while you loop over it breaks the loop. Waiting until the loop is finished makes it safe.

Only the code that added an object may remove it. That means there is one place that decides when the object ends, so a pointer you keep can never be left pointing at freed memory by someone else. A pointer that you keep after calling Remove would, so set it to nullptr.

The leak report at shutdown does what a memory checker does: it tells you who forgot to clean up.

World space and pixels

You place things in world units. The engine converts them to pixels when it draws.

World space

Units. Y points up. (0, 0) is the center of the screen. By default 1 unit is 50 pixels, so the window shows about 20 by 20 units.

Screen space

Pixels. Y points down. (0, 0) is the top-left corner. This is what GetMouseX() and the drawing functions use.

Engine functionUse it to
ConvertWorldPositionToPixels(pos)Find where to draw an object
ConvertPixelsToWorldPosition(px)Turn the mouse position into a world position
ConvertWorldLengthToPixels(len)Convert a radius or a width
ConvertPixelsToWorldLength(len)The reverse, for sizes

Vectors

A vector holds two numbers, x and y. There are four kinds, defined in src/Math/Vector.h:

TypeHoldsUse it for
Vector2ftwo floatsWorld positions and sizes, like Position. The default choice.
Vector2dtwo doublesThe same with more precision, when small errors add up.
Vector2itwo intsPixel positions on the screen.
Vector2utwo unsigned intsSizes and counts that are never negative.

They all support + - * / and have mag(), mag2(), norm(), perp(), dot(v), cross(v), reflect(normal) and lerp(v, t).

Camera

GetCamera() has three settings: Position (the world point shown at the center), Zoom (2.0 draws everything twice as big) and PixelsPerUnit. Every conversion above takes them into account, so objects follow the camera as long as you draw through those functions.

Why it works this way

Physics formulas have real units: a speed of 3 means 3 units per second, a gravity of 9.8 means 9.8 units per second squared. If you computed in pixels, the same simulation would behave differently at another window size or zoom.

Keeping simulation in world units and converting only at drawing time means the physics never knows what the screen looks like. Y points up in the world because that is how math and physics are written, so formulas copied from a textbook work as they are.

What happens in one frame

  1. Pre-updateDev tools read their keys and mouse clicks. The screen is cleared to black.
  2. UpdateThe time control decides whether the game runs. If it does: GameManager::Update, which ends by calling GameBase::Update to update every GameObject.
  3. Fixed updatesZero, one or several times, always 1/60 s: GameManager::FixedUpdate, which calls GameBase::FixedUpdate to run FixedUpdate on every GameObject. The physics step comes right after each one.
  4. Post-updatePending additions and removals are applied. Then Draw is called on every GameObject. This runs even while paused. The dev tools are drawn on top.

Order inside a frame matters: the code you write in GameManager::Update runs first, then GameBase::Update updates the objects.

Why it works this way

Additions and removals are applied after everything has updated and before drawing, so no object appears or vanishes in the middle of a frame, and the picture shows the state at the end of it. The dev tools draw last so they stay on top of the game.

Drawing is outside the "does gameplay run" check. That is what lets you pause and still see the scene.

Update and FixedUpdate

The GameManager and every GameObject have two functions that run during a frame:

FunctionRunsDelta timeUse it for
Update(elapsedTime)Once per frameThe real frame time. It changes every frame.Reading input, deciding what to do, anything that does not need to be exact.
FixedUpdate(fixedDeltaTime)Zero, one or several times per frameAlways 1/60 s.Applying forces and velocities, anything that feeds the physics.

The order inside a frame is always the same:

Update              once: read input, decide
FixedUpdate         repeated: apply forces and velocities
physics step        repeated: we add this in class, right after FixedUpdate
Draw                once: shows the result of this frame
Gameplay comes before the physics. Anything you decide, apply or change must be done before the simulation runs. A force applied after the physics step has no effect until the next step.

Call the base version

GameManager overrides Update and FixedUpdate from GameBase. The base versions are the ones that update every GameObject of the Scene, so your override must call them:

void GameManager::Update(Scene& scene, float elapsedTime)
{
    // your code: read input, decide what to do

    GameBase::Update(scene, elapsedTime);   // then update every GameObject
}

Without that line no object updates. Where you put the call sets the order: code before it runs before the objects, code after it runs after. This is the general rule for overriding a function in C++: unless you mean to replace what the parent does, call the parent's version.

A fast computer runs a frame in 3 ms, so most frames run no fixed step at all. A slow frame of 50 ms runs three. Either way the simulation advances 60 steps per second.

Why it works this way

Physics gives different results for different time steps. If the step changed with the frame rate, the same game would behave differently on every computer, and a large step can make the simulation explode. A constant step makes the simulation repeat exactly, which is also what lets you debug it.

Input goes in Update because a key press lasts one frame. A frame can run zero fixed steps, and the press would be missed, or two, and it would be applied twice. So Update notes what the player wants and FixedUpdate applies it.

A very long frame, like a stop at a breakpoint, is cut to 0.25 s. The game slows down for a moment instead of running hundreds of steps to catch up.

Pause and single step

The time control can stop gameplay while the screen keeps drawing. Use it to look at a situation frame by frame.

  • While paused, your Update functions do not run.
  • A step runs one Update and exactly one FixedUpdate, of 1/60 of a second, whatever the real frame time was.
  • Code you need to run even when paused (for example opening a menu) should not rely on elapsedTime from the game.

From code: GetTimeControl().SetPaused(true), TogglePause(), StepOneFrame().

Why it works this way

A step is always 1/60 s, not the real time since the last frame. A real frame time changes every frame, so two steps would never give the same result. With a fixed step, you can press F3 again and again, or call StepOneFrame(), and watch the exact same motion.

This is also how you will debug physics: pause, step one tick, and check where each object went.

Dev tools

A small toolbar at the top of the window has three buttons: pause, step and stats. The FPS number sits at the top right. The stats panel is hidden until you press its button.

F1 show or hide the tools
F2 pause or resume
F3 step, while paused

The stats panel shows FPS and frame time, object count, camera position, zoom and the mouse position in world units. The keys work even when the tools are hidden.

Why it works this way

The dev tools only display things and press the engine's own controls (time control, camera). They keep no game state. That means you can remove them, or hide them, and the game behaves the same.

They look at the real frame time, not the paused game time, so the FPS counter keeps moving while the game is stopped.

Avoid F1 to F3 in your game. The engine already uses them.

Rules to remember

  • Gameplay code goes in src/Game. Physics code goes in src/Physics.
  • Dependencies go one way: Game uses Engine, Engine uses Physics, Physics uses Math, Math uses nothing from src/. Run tools/CheckDependencies.ps1 to check it.
  • Engine code is open to you. Before changing it, be able to explain why the current design exists.
  • Position things in world units. Convert to pixels only when drawing.
  • Multiply movement by elapsedTime.
  • When you override Update or FixedUpdate in GameManager, call the GameBase version.
  • Y points up in the world and down on the screen.
  • Create objects with Scene::Add. Never new or delete a GameObject.
  • Whoever calls Add calls Remove, usually in Uninitialize. Set your pointer to nullptr afterwards.
